# Feature: Auth & Onboarding

## Purpose
Signup, login, sign out, and session-check routes. Email/phone are **unverified identification fields**; the credential is a password. No Supabase Auth library — authentication is plain verification of inputted values against the `users` table.

## User Flow
1. User opens the app → sees home; if not signed in, links to login/signup
2. Signup: name, password, email and/or phone, optional referral code → account created → session started → home
3. Login: identifier (email **or** phone) + password → session → home
4. Sign out → session cleared → home (signed out)
5. `GET /api/auth/me` returns the current user for session checks

## Rules
- At least one of email/phone required (DB-enforced)
- Email lowercased; phone trimmed, basic format `^\+?[0-9]{7,15}$`
- Password ≥ 6 chars, scrypt-hashed with a per-user random salt
- `referral_code` auto-generated: 8 chars from unambiguous alphabet (no I/O/0/1), unique
- Optional `referral_code` on signup → resolved against an existing user, sets `referrer`; self-referral rejected
- Duplicate email/phone → `409`; validation failure → `400`; bad credentials → `401` (generic message)
- User responses never include `password_hash`
- Session: HMAC-SHA256-signed token in an httpOnly cookie, 7-day expiry
- `users` is a standalone account table: id generated by the DB, no FK to `auth.users`
- All DB access happens server-side (API routes) via PostgREST; no client-side Supabase usage
